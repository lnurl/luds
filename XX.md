LUD-XX: `nodePubkeys` for `payRequest`.
=========================================

`author: andrerfneves` `discussion: TBD`

---

As LNURL-pay has become the dominant interface for Lightning payments across wallets and services, invoices are increasingly presented to users through abstractions — embedded browsers, in-app WebViews, platform relays and aggregated UIs — where the direct TLS connection between wallet and LNURL endpoint is no longer visible or auditable by the user.

Simultaneously, wallets have begun simplifying the payment confirmation screen, often showing only the amount and a short description, with the invoice itself hidden behind a tap. This creates an opening for invoice substitution attacks that are difficult for users to detect.

This LUD adds an optional field to the [LUD-06](06.md) payRequest response that allows a `SERVICE` to advertise the public keys of the Lightning nodes that may generate invoices for this endpoint. A `WALLET` that implements this LUD can verify that a received BOLT11 invoice was created by an expected node, providing an additional layer of security without requiring any changes to the invoice payment flow.

## `nodePubkeys`

An optional field `nodePubkeys` is added to the initial payRequest response:

```diff
 {
     "callback": "https://service.com/api/lnurl/pay/cb",
     "maxSendable": 100000000,
     "minSendable": 1000,
     "metadata": "[[\"text/plain\",\"Pay to Service\"]]",
     "tag": "payRequest",
+    "nodePubkeys": [
+        {
+            "pubkey": "02e7b2d5c9d1579c2fa2d1f5a6a3b8f4e9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5"
+        }
+    ]
 }
```

`nodePubkeys` is an optional array. If provided, it MUST contain at least one entry. If absent, `WALLET` behavior is unchanged from LUD-06 — no verification is performed.

Each entry in the array is an object that MUST contain the following field:

- `pubkey` (string, required): A hex-encoded compressed secp256k1 public key (66 hex characters) representing the public key of a Lightning node that may generate invoices at this endpoint's `callback`.

Entries MAY contain additional fields. Future LUDs may define new fields on these objects. A `WALLET` MUST ignore any fields it does not recognize.

## Wallet verification flow

When a `WALLET` that implements this LUD receives a payRequest response that includes `nodePubkeys`:

1. The `WALLET` MAY cache the `nodePubkeys` list for the duration of this payment flow.

2. The `WALLET` proceeds with the standard LUD-06 flow: user selects an amount, `WALLET` calls `callback?amount=<milliSatoshi>`.

3. The `WALLET` receives the callback response containing `pr` (the bech32-serialized BOLT11 invoice).

4. The `WALLET` extracts the payee node public key from the BOLT11 invoice using one of the following methods, in order of preference:

   a. **`n` field (payee node ID)**: If the invoice contains the `n` field as defined in BOLT11, this 33-byte compressed public key SHOULD be used directly.

   b. **Signature recovery**: If the invoice does not contain the `n` field, the public key MAY be recovered from the invoice signature by using the recovery bit (contained in the `rec` field of the signature). This is functionally equivalent and produces the same result.

   ```python
   # Example: extracting payee pubkey from a BOLT11 invoice
   from bolt11 import decode
   invoice = decode(pr)
   # If n field exists:
   payee_pubkey = invoice.payee  # hex string, 66 chars
   # Otherwise recover from signature:
   if payee_pubkey is None:
       payee_pubkey = invoice.recover_payee_pubkey()
   ```

5. The `WALLET` compares the extracted payee pubkey against all entries in the `nodePubkeys` array, checking `entry.pubkey` for each.

6. If the payee pubkey **matches** one of the advertised `nodePubkeys`, the `WALLET` proceeds with payment as normal.

7. If the payee pubkey **does not match** any advertised `nodePubkeys`, the `WALLET` SHOULD display a clear, non-blocking warning to the user. Example warning text:

   > "This invoice was not generated by an expected node. The service advertised one set of nodes, but this invoice came from a different node. Proceed only if you trust the recipient."

   The `WALLET` SHOULD NOT block payment on this mismatch. The user must remain in control.

8. If the `WALLET` has a cached `nodePubkeys` set from a prior session for the same LNURL, and the current set differs, the `WALLET` MAY display an informational notice about key rotation. A `WALLET` SHOULD NOT treat key rotation as suspicious — services change nodes for legitimate operational reasons.

## Extensibility

The `nodePubkeys` array uses objects rather than raw strings to allow forward-compatible addition of per-key metadata.

### Reserved future fields

| Field | Type | Description |
|-------|------|-------------|
| `alias` | string | Human-readable node name (e.g. "Kraken LN Primary") |
| `since` | number | UNIX timestamp when this key was first used |
| `signature` | string | Cryptographic proof binding this pubkey to the LNURL domain |
| `features` | number | Bitfield of supported BOLT9 feature bits |



## Reference: extracting payee node ID from BOLT11

BOLT11 invoices include an optional `n` field carrying the payee's 33-byte compressed public key. When present, this is the authoritative source.

When the `n` field is absent — common for invoices from some implementations — the payee public key can be recovered from the ECDSA signature via the recovery ID (compact signature format).

Most Lightning libraries expose one or both methods:

- **LND**: `invoice.Destination`
- **CLN**: `decodepay` returns `payee` if present
- **lnurl-node (Node.js)**: `decode(pr).payeeNodeId` or `recoverPayeeNodeId(pr)`
- **rust-lightning**: `invoice.payee_pub_key()` returns `Option`
